# Генерация и проверка качества: текущий этап

## Что проверено

Автоматические протокольные тесты работают с синтетическими ответами и имитацией транспорта, без сетевых запросов. Они подтверждают поведение кода при заданных ответах, но не качество реальной модели и не её устойчивость к инъекциям. Дополнительно подключена настоящая локальная Qwen3-4B-Instruct через Ollama; настройка описана в [LOCAL_MODEL.md](LOCAL_MODEL.md). Конкурсная Qwen3.8-27B — другая модель, её результаты нужно проверять отдельно.

Реализованы две независимые по назначению проверки:

1. Техническая: корректный HTTP-запрос по примеру организаторов, таймауты, ошибки API, строгий JSON, реальные ID источников, лимит ответа, очевидные новые числа, отсутствие самовольного создания заявок, реакция на отказ от контактов. Некорректный результат Critic не считается одобрением.
2. Содержательная: разбор конкретных ответов по эталонным примерам. После подключения API можно запустить отдельного модельного судью с критериями подтверждённости, релевантности, контекста и обращения с заявками. Эталоны отправляются только судье, генератор их не получает.

Семантический Critic — отдельный вызов той же настроенной модели, не независимый источник истины. Его одобрение требует содержательной проверки. Проверка одного только совпадения ID/чисел не выявляет неверный субъект, единицы, отрицания или пропущенные оговорки.

## Текущая проверка фактических ответов: 30 запросов

Повторно запущены 18 предоставленных демовопросов и 12 дополнительных сценариев: АСКУЭ, сведения о предприятии, допуск к оптовому рынку, гарантии, питание при отключении сети, доказательство хищения, размещение платформы, поддерживаемые ресурсы OCR, отказ от телефона и границы компетенции.

Режим — `extractive`, реальных запросов к LLM не было. Использовались текущий код и предоставленная БЗ, без подмены ответов генератора. Все 30 ответов просмотрены Codex: демовопросы сравнены с предоставленными эталонами, дополнительные — с соответствующими ограничениями БЗ. Это предварительная оценка, а не результат конкурсного судьи.

| Релевантность на этом наборе | Количество |
|---|---:|
| Прямой ответ | 12 |
| Частичный ответ | 14 |
| Не отвечает по существу | 4 |

По отдельной строгой рубрике полноты существенные пункты раскрыты в 4 ответах. Релевантность и полнота не объединяются в «процент качества». Все ответы укладываются в 150 слов; 28 имеют реальные ID источников, ещё два относятся к маршрутам передачи специалисту/отсутствия сведений.

Подтверждены проблемы извлечения: вместо законченного ответа попадают названия полей таблицы; найденная цитата отвечает на соседний вопрос; в диалогах теряется запрошенная проверка или список данных для оценки. `extractive_grounding_passed` подтверждает принадлежность текста источнику, но эти смысловые ошибки не обнаруживает.

АСКУЭ выбирает документ платформы, а явно сообщённые производственный тип предприятия и цель снижения расходов извлекаются корректно. Эти случаи и сценарий отказа от телефона дополнительно прогнаны через настоящий HTTP-обработчик с временной SQLite: HTTP-ответы совпали с прямыми вызовами, факты сохранились, заявки не создавались.

Полные запросы, фактические ответы, эталоны/ожидания, источники и замечания сохранены локально в игнорируемом `data/agent_answers_review.md` и `data/agent_answers_quality_report.json`; HTTP-прогон — в `data/agent_answers_http_review.json`. Закрытые материалы в Git не добавлялись. Исходники AI при этой содержательной проверке не менялись.

Приоритеты исправления: исключить неполные поля таблиц и ссылки на отсутствующий контекст; выбирать фрагмент по запрошенному свойству, а не только по продукту; формировать конкретный следующий вопрос с учётом истории и фактов. Первый реальный генеративный прогон описан ниже; полноценная оценка конкурсной модели остаётся отдельной работой.

## Реальная локальная Qwen3-4B-Instruct: 16 ноября 2026

Запущена `qwen3:4b-instruct-2507-q4_K_M` в официальном Ollama на CPU, с лимитами контейнера 8 CPU и 12 ГиБ RAM. Вызовы проходили через настоящий локальный OpenAI-совместимый HTTP API. Ответы генератора и Critic сохранены локально; эталоны генератору не передавались.

Первый запуск обнаружил повторяемую ошибку: модель возвращала внутренний `chunk_id` вместо документного `source_id`. Проверка корректно отклоняла такой черновик. Из данных для модели убран конкурирующий идентификатор фрагмента, а требование копировать `source_id` уточнено. Неизвестные идентификаторы по-прежнему отклоняются.

Следующий прогон шести случаев: АСКУЭ, производственное предприятие и снижение расходов, два тарифа OCR, год выпуска, тепло/газ и отказ от телефона при запросе оценки стоимости.

| Технический результат этого прогона | Количество |
|---|---:|
| Реальные модельные ответы, одобренные Critic | 6 |
| Запасные extractive-ответы | 0 |
| Ошибки API/JSON/ID | 0 |
| Ответы более 150 слов | 0 |

Задержка одного хода с генерацией и Critic составила 53–80 секунд. Явные факты предприятия извлечены: `industry=manufacturing`, `goal=reduce_energy_costs`.

**Ручная проверка не подтвердила безошибочность Critic.** Все шесть ответов по существу относятся к вопросу, но только три признаны полными по строгой предварительной рубрике Codex. В ответе о годе выпуска модель добавила неподтверждённую точность «более 90%», а Critic её одобрил. В ответе об оценке повторно запрашивалось уже сообщённое количество приборов, добавлялись лишняя цена и чрезмерное обобщение об инфраструктуре. Рекомендация выхода на оптовый рынок до выяснения мощности остаётся предварительной, хотя порог и уточнение указаны.

После найденной числовой ошибки уточнены оба промпта: не добавлять неспрошенные точности и цены; сверять число с конкретным параметром, ресурсом и условием; при любом неподтверждённом утверждении отклонять ответ целиком. Это улучшение инструкции, а не доказательство надёжности семантической проверки.

Вопрос о годе выпуска повторён на настоящей модели с новыми промптами: получен корректный ответ о распознавании года без выдуманной точности, без fallback, за 69 секунд. Результат сохранён в `data/ai_local_model_year_recheck.json`. Все шесть вопросов с новыми промптами заново не прогонялись; исходная оценка выше относится именно к первому набору ответов.

Перед коммитом отдельно проверен настоящий вызов `answer_question` из 12 экспортированных корневых модулей: временная папка вне репозитория, Python с `-S`, без импортов `ai`, backend, FastAPI, SQLite или frontend. Диалог об оценке стоимости получил модельный ответ с реальными ID и без предложенного действия за 87 секунд. Технический контракт прошёл, но замечание о контексте сохранилось: модель повторно перечисляет уже сообщённое количество, добавляет неспрошенную цену и чрезмерное обобщение об инфраструктуре; Critic это одобряет. Отчёт — `data/ai_precommit_flat_live.json`. Эти ограничения не считаются исправленными.

Через запущенный Docker-backend с новыми промптами дополнительно выполнены два настоящих `/api/chat` в новых сессиях. АСКУЭ получила содержательный ответ с источником `20-products/22-askue.md`. Вторая сессия сохранила в общей SQLite `industry=manufacturing`, `goal=reduce_energy_costs`. В обеих сессиях создано ноль заявок. Задержки — 91 и 70 секунд; HTTP-ответы и проверка сохранённых фактов находятся в `data/ai_local_model_http.json`. Диагностический debug для этих HTTP-запросов не включался, поэтому этот отчёт не заменяет отдельный учёт генерации/fallback в прямом прогоне ядра.

Локальные закрытые артефакты: `data/ai_local_model_checks.json` (ответы и реальные ответы API), `data/ai_local_model_review.md`, `data/ai_local_model_manual_review.json` (оценки привязаны к хешам), `data/ai_local_model_quality.json`. Полный набор из 18 или 30 вопросов на реальной модели пока не запускался; шесть случаев не заменяют такую оценку. Итоговый общий технический прогон: 117 тестов и 63 подпроверки прошли; одно предупреждение Starlette/httpx.

## Предварительный разбор baseline

Разобраны 18 фактических ответов относительно предоставленного `demo_output.csv`. Метод `codex_manual_review`: предварительная оценка агентом, не экспертная разметка и не результат LLM-судьи платформы.

| Релевантность | Количество |
|---|---:|
| Прямой ответ на вопрос | 7 |
| Частичный ответ | 9 |
| Не отвечает по существу | 2 |

По строгому критерию полноты только один ответ раскрывает все существенные пункты эталона. Это не конкурсная оценка: отсутствие необязательного уточнения и неверный факт не равноценны, поэтому релевантность, полнота и контекст отмечаются отдельно, без единого «процента качества».

Главные найденные проблемы:

- Название поля таблицы иногда выдаётся вместо законченного ответа.
- Цитата относится к нужному продукту, но отвечает на соседний вопрос.
- В диалогах теряются конкретная ценовая категория, вечерний профиль и смешанная схема сбора показаний.
- Отказ от телефона принят корректно, но дальнейшие сведения для оценки объекта не перечислены.
- Ограничения иногда остаются в отсутствующем фрагменте «выше», а ответ не поясняет их.

Отчёты остаются локально в игнорируемом `data/`: `ai_eval_baseline.json`, `ai_manual_review.json`, `ai_quality_report.json`. Разметка привязана к SHA-256 точного текста ответа: после изменения ответа старая оценка отклоняется. Тексты закрытых данных в этот документ не копируются.

## Локальные команды без API

```bash
PYTHONPATH=tests python -m unittest \
  test_ai_contract test_retrieval test_facts test_generation test_quality_eval -v

python -m scripts.eval_quality \
  --answers data/ai_eval_baseline.json \
  --questions 'Данные-20261109T121228Z-1-001/Данные/demo_questions.csv' \
  --references 'Данные-20261109T121228Z-1-001/Данные/demo_output.csv' \
  --manual-review data/ai_manual_review.json \
  --output data/ai_quality_report.json
```

Локальные отчёты и разметка не входят в Git. Если их нет, сначала сформируйте ответы через `scripts.eval_ai`. Запуск `eval_quality` без `--manual-review` и без `--judge` создаёт лист ожидания проверки, не положительную оценку. Для ручной разметки JSON содержит `method` и `reviews`: объект по ID вопроса с полями `answer_sha256`, `relevance`, `completeness`, `context` (целые 0/1/2), `comment`. Метод разметки должен явно указывать автора; текущая разметка выполнена Codex.

## Модельный прогон

Настроить `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` в окружении. Для локальной Qwen импортировать `data/local_model.env` по инструкции [LOCAL_MODEL.md](LOCAL_MODEL.md). При конкурсной проверке платформа сама передаёт адрес прокси, идентификатор модели и служебный ключ; личный ключ участника не нужен. Модуль и скрипты не загружают `.env` сами. Адрес и ключи в отчётах не сохраняются.

Первый прогон — три вопроса; затем тот же набор из 18. Обрабатывать успех генератора, одобрение Critic и выдачу запасной цитаты как разные результаты:

```bash
python -m scripts.eval_ai --mode llm --limit 3 \
  --kb 'Данные-20261109T121228Z-1-001/Данные/knowledge-base.zip' \
  --questions 'Данные-20261109T121228Z-1-001/Данные/demo_questions.csv' \
  --output data/ai_model_smoke.json

python -m scripts.eval_ai --mode llm \
  --kb 'Данные-20261109T121228Z-1-001/Данные/knowledge-base.zip' \
  --questions 'Данные-20261109T121228Z-1-001/Данные/demo_questions.csv' \
  --output data/ai_model_answers.json

python -m scripts.eval_quality --judge \
  --answers data/ai_model_answers.json \
  --questions 'Данные-20261109T121228Z-1-001/Данные/demo_questions.csv' \
  --references 'Данные-20261109T121228Z-1-001/Данные/demo_output.csv' \
  --kb 'Данные-20261109T121228Z-1-001/Данные/knowledge-base.zip' \
  --output data/ai_model_quality.json
```

При отсутствии конфигурации команды модельного режима завершаются явной ошибкой до обработки вопросов. Сетевые ошибки судьи учитываются отдельно от отклонённых ответов и не включаются в число успешно оценённых. Локальный прогон не подтверждает доступ к конкурсному прокси и качество конкурсной модели.

Проверить вручную все спорные ответы и отдельно сравнить: прямой ответ, полноту оговорок, работу с контекстом, количество неподтверждённых утверждений, долю запасных ответов, задержку и ошибки API. Задержка локального извлечения не предсказывает задержку генерации: модельный ход делает до двух последовательных запросов.
