# AI-вызов для конкурсного solution.py

## Согласуемый интерфейс

```python
def answer_question(question: str, knowledge_base: str | Path) -> str:
    ...
```

Каноническая реализация: `ai/submission.py`. В репозитории импортируется как `from ai.submission import answer_question`, в плоском конкурсном экспорте — как `from energytool_ai import answer_question`.

- `question`: отдельный вопрос либо короткий диалог внутри строки, со строками `Пользователь:` / `Ассистент:` (также `user:` / `assistant:`). Обрабатывается последняя реплика пользователя.
- `knowledge_base`: явный путь к ZIP с Markdown/TXT или к каталогу таких файлов. Дополнительно поддерживается JSON-индекс, созданный нашим `scripts.build_index`.
- Результат: непустой готовый текст, пробельные символы нормализованы в одну строку. Это не JSON AI-контракта и не готовая CSV-строка: экранирование и сохранение CSV выполняет `solution.py`.

Вызов использует общее ядро `answer_turn`, включая поиск, Planner, извлечение фактов и Critic. Каждая обработка начинается с пустыми историей и фактами; внутри переданного диалога контекст сохраняется. Между независимыми вопросами кешируется только неизменяемая структура БЗ. Параллельные вызовы с разными путями БЗ не меняют глобальные переменные окружения и не подменяют друг другу документы.

Конкурсный вызов включает модельный режим для себя. `AI_MODE=extractive`, `AI_INDEX_PATH` и `AI_KB_PATH` веб-приложения не переопределяют явно переданную БЗ и не отключают модель в `answer_question`. Публичная сигнатура `answer_turn` и поведение backend не изменены.

## Подготовка модулей в корне ZIP

Из корня репозитория:

```bash
python -m scripts.export_ai_modules --output data/submission_ai
```

В папке появляются 12 `.py`-файлов:

```text
energytool_ai.py
energytool_ai_consultant.py
energytool_ai_critic.py
energytool_ai_dialogue.py
energytool_ai_facts.py
energytool_ai_generation.py
energytool_ai_llm.py
energytool_ai_planner.py
energytool_ai_prompts.py
energytool_ai_retriever.py
energytool_ai_schemas.py
energytool_ai_topics.py
```

Все относительные импорты AST-преобразованием заменяются на импорты соседних модулей. Префикс уменьшает риск конфликта с именами других модулей. Экспорт воспроизводится из текущего `ai/`: поддерживать вторую копию алгоритмов вручную не требуется.

В итоговый ZIP backend-разработчик помещает **содержимое** этой папки рядом со своим `solution.py`, не сам каталог `submission_ai/` и не папку `ai/`. Экспортёр не создаёт `solution.py`, `requirements.txt`, CSV или конкурсный ZIP. AI использует только стандартную библиотеку Python 3.11+, новых сторонних зависимостей не требует.

Повторный экспорт одинакового кода допустим. Если существующие сгенерированные файлы отличаются, используйте новую папку либо явный `--overwrite`; он заменяет только имена сгенерированных модулей. Другие файлы каталога не удаляются. Не редактируйте сгенерированные модули: меняйте исходники в `ai/` и повторяйте экспорт.

`data/` исключён из Git. Экспортируются только исходные `.py`; ключи, `.env`, документы, индекс и вопросы в экспорт не включаются. JSON-индекс содержит текст БЗ: для конкурса используйте переданный платформой `DATA_DIR/knowledge-base.zip`, а не упаковывайте такой индекс как открытый исходный файл.

## Вызов из скрипта backend-разработчика

После размещения всех экспортированных модулей в корне архива:

```python
import os
from pathlib import Path
from energytool_ai import answer_question

kb_path = Path(os.environ.get("DATA_DIR", "data")) / "knowledge-base.zip"
answer = answer_question(question, kb_path)
```

Чтение входных строк, выбор имён входных файлов, сохранение исходных ID, обработка ошибок отдельных строк, пул потоков и формирование `submission.csv` остаются в `solution.py`. AI-функция не читает `questions.csv`, не создаёт файлов результата и не обращается к общей SQLite или HTTP-backend.

## Переменные организаторов

| Назначение | Переменные и приоритет |
|---|---|
| Корень API | `LLM_BASE_URL`, затем `BASE_URL`, затем `OPENAI_BASE_URL` |
| Ключ | `LLM_API_KEY`, затем `OPENAI_API_KEY` |
| Модель | `LLM_MODEL`, затем `GEN_MODEL`, затем `OPENAI_MODEL` |
| Предел токенов | `MAX_TOKENS`: 1–8192, по умолчанию 1600 |
| Температура | `TEMPERATURE`: 0–2, по умолчанию 0 |
| Кандидаты поиска | `TOP_K`: 1–30, по умолчанию 8 |
| Таймаут запроса | `AI_LLM_TIMEOUT_SECONDS`: больше 0, не более 120; по умолчанию 25 секунд |

Адрес, ключ и имя модели должны быть заданы для модельного маршрута. Пустые значения и одноимённые placeholders (`LLM_MODEL=LLM_MODEL`) пропускаются при выборе алиасов, как в примере организаторов. `.env` самостоятельно не читается. Адрес — корень API, к которому добавляется `/chat/completions`. SDK OpenAI не используется.

Генерация учитывает полный `MAX_TOKENS`, без фиксированной обрезки до 384/1600 при явно заданном большем значении. Для Critic бюджет дополнительно ограничен 1000 токенами и никогда не превышает `MAX_TOKENS`. На модельном маршруте выполняется до двух последовательных запросов: генерация и отдельная проверка. Число параллельных вопросов (`MAX_WORKERS`) регулирует внешний скрипт, AI не создаёт свой пул.

Текущий поиск лексический: `EMB_MODEL`, `RERANKER_MODEL`, `EMBEDDER_API_KEY`, `RERANKER_API_KEY` пока не используются. `CHUNKER` из учебного примера также не используется: работает разбиение нашего ядра по заголовкам и абзацам.

## Ошибки и проверка

Неправильный путь БЗ, пустой вопрос, некорректные настройки или отсутствие конфигурации требуемой модели вызывают исключение. Имена исключений — часть внутренних модулей; скрипт может перехватить ошибку отдельной строки по своей политике. При транспортной ошибке модели, неверном ответе или отклонении Critic ядро возвращает исходный extractive/уточняющий fallback, а не невалидный черновик. Приветствия и маршруты, не требующие продуктовой генерации, могут завершаться без запроса к API.

Локальные проверки без сети:

```bash
PYTHONPATH=tests python -m unittest test_submission -v
```

Проверяется в том числе временный плоский архив: распаковка, запуск отдельного Python с `-S` вне репозитория, импорт `energytool_ai`, имитация двух API-вызовов и отсутствие импортов `ai`, FastAPI, SQLite и backend. Также проверяются параллельные БЗ, изоляция кейсов, переменные API, бюджеты и сохранение глобального окружения.

Реальный API организаторов пока недоступен. Эти тесты подтверждают интеграцию кода и протокол на имитации ответов; качество генерации и фактическую совместимость сервера необходимо проверить после выдачи доступа.
